# Database reliability and migration runbook

Phase 2.6 introduces explicit Alembic migrations. These instructions are operator procedures, not authorization to access production. Implementation and automated tests use only newly created disposable local PostgreSQL clusters. Production schema, server version, record counts, backup capabilities, and orphan count have not been inspected.

## Safety boundaries

- Application import/startup performs no schema creation or migrations. An empty database must be initialized explicitly before the API serves database-backed requests.
- Tools never load `.env`. Supply `MIGRATION_DATABASE_URL` explicitly through a trusted environment/secret mechanism. `DATABASE_URL` is not a fallback. An explicit host, database, and username are required; nonempty libpq `PG*` overrides and target-changing URL options are rejected. Never echo, paste into shell history, or pass a credentialed URL as a command-line argument.
- Commands below intentionally omit connection values. They must not be run until the operator has verified the database identity privately and received the appropriate approval.
- The only automated schema changes are inside disposable test clusters. CI never uses hosting credentials.
- No orphan cleanup, reassignment, account recovery, sequence repair, production seeding, or credential rotation is automatic.
- The operator wrapper accepts exact known revisions only. Direct Alembic execution, offline execution, `stamp head`, and downgrade to `base` are disabled. Baseline downgrade itself also raises rather than dropping tables.
- A session advisory lock permits one cooperating migration operator per database. It does not stop unrelated SQL tools or application writes. Keep one designated operator and prevent other schema changes during the procedure.

## Revision chain

| Revision | Upgrade | Downgrade to predecessor |
| --- | --- | --- |
| `0001_legacy_baseline` | Create legacy tables/indexes on an empty public schema | Prohibited: would destroy application data |
| `0002_owner_index` | Concurrent nonunique B-tree index `ix_internships_user_id` | Concurrently drop only this index |
| `0003_owner_foreign_key` | Named `ON DELETE RESTRICT` FK, initially `NOT VALID` | Drop only the ownership FK |
| `0004_validate_owner_fk` | Check orphan count and validate FK | Reinstall the same FK as `NOT VALID` in one transaction |

`users` retains integer sequence-backed IDs, unique non-null username, and password hash. `internships` retains all legacy fields and IDs. No columns, API routes, or application records are removed or rewritten. New ORM declarations match the final migrated schema. Preserve historical revision files and their legacy schema-contract checks when adding future migrations; do not redefine the baseline from later models. Models are registered through `schema.py` without importing application configuration.

The owner index is separate from primary-key indexes, which are preserved for compatibility. The foreign key is named `fk_internships_user_id_users`, nondeferrable, with `ON DELETE RESTRICT` and default `ON UPDATE NO ACTION`. There is no ORM delete cascade. A future account-deletion feature needs a separate retention/deletion design.

## Read-only preflight

With the explicitly approved target in `MIGRATION_DATABASE_URL`:

```bash
venv/bin/python -B scripts/schema_preflight.py --stage legacy --require-unversioned
```

The checker starts a repeatable-read, read-only transaction. It checks public application tables, exact columns/types/nullability/defaults, primary keys, uniqueness, index definitions/options/validity, foreign-key shape/validation state, owned sequence state, unexpected tables/views/checks/custom triggers/RLS, and disabled internal triggers. It reports fixed diagnostic codes and aggregate user/application/orphan counts, never rows, password hashes, usernames, URLs, or driver errors. It does not advance sequences.

`ok: true` at legacy/indexed/protected stages means the structural contract passed; **inspect `orphaned_internships` separately**. Orphans are permitted before validation so records can remain untouched. Use a separately authorized private investigation if the count is nonzero.

This checker is deliberately conservative. Any unexpected legitimate extension, identity-column substitution, additional public table, custom index, privilege limitation, or schema mismatch requires review. It does not automatically normalize production. It is not a full audit of all schemas, grants, extensions, replication, server configuration, or arbitrary custom database objects.

The legacy contract expects the schema generated by the old model: public tables, SERIAL-style owned sequences, unbounded VARCHAR fields, and the two legacy `ix_*_id` indexes. Do not stamp a database with a materially different schema merely because its API currently works.

## Backup and rehearsal gate

Before any production connection or mutation, obtain separate approval. Then:

1. Privately verify host/database/role identity, PostgreSQL major version, ownership/DDL privileges, schema, storage headroom, table sizes, current workload, and any existing revision state. Use a direct PostgreSQL session endpoint; session advisory locks are incompatible with transaction-pooling proxies.
2. Verify the provider's available backup/PITR options; do not assume the current Render plan supplies them. Define recovery-point and recovery-time expectations with the owner.
3. Make a consistent custom-format `pg_dump` using tools compatible with the server. Use a protected libpq service/password file or secure operator environment; never include a password or URL on the command line. Retain roles/ownership/grant information separately if needed.
4. Store the backup encrypted, access-restricted, outside Git and outside public build artifacts. Review failure output privately. Do not commit dumps, backup manifests containing credentials, or restored records.
5. Verify the archive with `pg_restore --list`, then restore into a separately authorized isolated environment and check schema, counts, representative data, sequences, and login compatibility. A backup is not considered verified just because a file exists.
6. Rehearse the migration sequence on the same PostgreSQL major version as production. The automated suite uses synthetic records; a private production-backup restore requires separate authorization and access controls.
7. Agree on a low-traffic window and write pause if required by measured lock/load behavior. Do not claim zero downtime. Keep a record of backup identity/time, code revision, schema revision, and approvals without secret values.

## Baseline an existing database

After the backup/rehearsal gates and explicit approval:

```bash
venv/bin/python -B scripts/schema_preflight.py --stage legacy --require-unversioned
venv/bin/python -B scripts/migrate.py baseline
venv/bin/python -B scripts/schema_preflight.py --stage legacy
```

The baseline command repeats the schema check while holding the migration advisory lock, then stamps **only `0001_legacy_baseline`**. It creates migration bookkeeping, not application tables or records. Existing migration bookkeeping, drift, or inspection errors stop this operation. The checker output alone is not authorization.

The baseline's CREATE TABLE upgrade is for empty databases only. Never run it as a replacement for baselining populated tables. Schema drift requires a reviewed reconciliation plan; do not reset tables, regenerate a guessed baseline, or stamp the final revision to hide drift.

For a new empty local database, initialize explicitly instead:

```bash
venv/bin/python -B scripts/migrate.py upgrade 0001_legacy_baseline
```

Afterward use the same incremental steps below. Do not point these commands at an ordinary local developer database during the Phase 2.6 verification task; its tests create their own clusters.

## Incremental upgrade

Run each command separately and inspect its result before proceeding:

```bash
venv/bin/python -B scripts/migrate.py upgrade 0002_owner_index
venv/bin/python -B scripts/schema_preflight.py --stage indexed
venv/bin/python -B scripts/migrate.py upgrade 0003_owner_foreign_key
venv/bin/python -B scripts/schema_preflight.py --stage protected
```

At this point new invalid ownership inserts/changes are rejected by PostgreSQL, but historical orphans may still exist. Normal unrelated edits of an existing orphan may not trigger an ownership recheck; this interim state is not a claim of fully validated integrity.

If and only if the orphan count is zero and the previous stages passed:

```bash
venv/bin/python -B scripts/migrate.py upgrade 0004_validate_owner_fk
venv/bin/python -B scripts/schema_preflight.py --stage validated
venv/bin/python -B scripts/migrate.py current
venv/bin/python -B scripts/migrate.py check
```

`current` and `check` run with database read-only transactions and cannot create missing migration bookkeeping. `check` compares the database with current ORM metadata without applying changes. Preflight adds checks such as constraint validation/index validity that ORM comparison does not establish.

## Orphan remediation policy

The count query uses `NOT EXISTS` between `internships.user_id` and `users.id`. It reveals no row contents. A nonzero count blocks validation and does not delete or change records.

Preserve orphans in place. Investigate original ownership privately using authoritative evidence and approved backups. Do not attach records to an arbitrary existing account or shared recovery account, which could expose private data. Restoring a genuinely missing user or correcting proven ownership requires a separate reviewed data-change plan, backup, explicit approval, and sequence checks. If ownership cannot be established, retain the rows and stay at the protected revision. Report integrity as pending rather than bypassing validation. No remediation script is provided.

## Locks and timeouts

| Operation | Expected impact |
| --- | --- |
| Baseline stamping | Brief migration bookkeeping writes; schema inspection can wait on conflicting DDL |
| `CREATE INDEX CONCURRENTLY` | Allows normal writes, but adds scans/I/O and waits for relevant transactions; cannot run in a normal transaction |
| FK `ADD ... NOT VALID` | `SHARE ROW EXCLUSIVE` on both tables; can block writes, despite avoiding the historical scan |
| `VALIDATE CONSTRAINT` | Historical scan, `SHARE UPDATE EXCLUSIVE` on internships and a referenced-table lock; normal DML generally continues, other maintenance/DDL may wait |
| FK drop/reinstallation | Stronger table locks, including `ACCESS EXCLUSIVE`; use a reviewed maintenance window |
| Concurrent index drop | Nontransactional operation, waits/load possible; separate recovery point |

Connections use a 5-second connect timeout, 3-second lock timeout, and 60-second statement timeout. A reviewed operator can set `MIGRATION_STATEMENT_TIMEOUT_SECONDS` from 1 to 3600 for a measured larger scan/build; this does not disable the lock timeout. A timeout is a stopping condition, not permission to retry repeatedly or kill other sessions.

Alembic uses a transaction per revision. The concurrent-index autocommit block commits outside normal transactional DDL, so a multi-revision upgrade is **not globally atomic**. Previously completed revisions remain committed if a later revision fails. Prefer exact step-by-step targets in production.

## Exact stopping conditions

Stop before the next step if any of these apply:

- Target identity, approval, backup/recovery verification, required privileges, storage headroom, or production PostgreSQL compatibility is unknown.
- Preflight fails, cannot inspect an object, times out, detects unexpected schema/version/defaults/indexes/constraints/triggers/RLS, or finds a sequence behind existing IDs.
- Another operator holds the advisory lock or an operation hits a lock/statement timeout.
- A concurrent index exists unexpectedly, is invalid/not ready, or its definition differs; never treat name existence as success.
- The command fails or the expected revision and schema stage disagree, including a committed index with an older revision marker.
- Orphans remain before validation; constraint validation fails; or a constraint has disabled enforcement triggers.
- Row counts/data verification change unexpectedly (account for explicitly controlled concurrent writes), normal API behavior regresses, or database errors/load rise during the window.

Do not advance the revision marker to force progress. CLI errors deliberately omit driver details to prevent credential/record leakage. Inspect fixed preflight codes, expected revision, and index state first; any deeper diagnostics must remain private and reviewed.

## Failure recovery and rollback

- **Transactional failure:** the current revision rolls back; earlier successful revisions remain. Inspect the actual revision and schema state before resuming.
- **Concurrent-index failure:** an invalid index, a valid index without its version marker, or a completed drop with an older marker may remain. Stop. A separate approved recovery must identify the exact phase-owned object and definition. For failed creation, the preferred rehearsal-tested recovery is to remove only the verified new index concurrently, confirm the legacy stage, then rerun the index revision. Never automatically drop unrelated indexes. After an interrupted downgrade/drop, reconcile the object and marker through a separately reviewed repair; no generic stamp shortcut is provided.
- **Orphan validation failure:** leave the protected FK in place; preserve all rows and resolve ownership separately. No rollback is required merely because validation is pending.
- **Application rollback:** the old application is compatible with the additive index/FK; keep them when possible. Its startup `create_all()` will not remove them, but restoring that older build also restores its old authentication/error behavior. Diagnose before choosing a code rollback.
- **Reviewed schema rollback:** downgrade to `0003_owner_foreign_key` to return to unvalidated protection; downgrade to `0002_owner_index` to remove the FK; downgrade to `0001_legacy_baseline` to remove the index. These operations retain application rows, but reduce protection/performance and involve locks. Stop after each and run the matching preflight. No production rollback has been performed.
- **Never downgrade past the baseline.** Do not delete migration bookkeeping or use table resets. Backup restoration is disaster recovery, requires a separately approved cutover/write-freeze plan, and can lose post-backup writes. Restore into a new isolated database first; never blindly overwrite the live database.

## Maintenance during a database cutover

The new [application-level maintenance runbook](MAINTENANCE_CUTOVER.md) supplies a free-hosting write gate and explicit old-instance retirement checks. Its PostgreSQL read-only setting is transaction-scoped and applies only to runtime ORM sessions; migration/admin tools remain separately controlled. It does not authorize new migrations, create a database-wide fence, or make an older ungated instance safe. The owner has separately reported completing the Neon migrations; do not repeat stamps/upgrades as part of a cutover.

## Backend release ordering and verification

After separate approval for deployment/migrations, make migration files available to the designated operator without changing the running service first. Pushing the linked branch may automatically deploy; coordinate hosting auto-deploy behavior explicitly before any push. This repository does not configure a production migration hook.

Prefer installing the missing-user protection release before the FK step if historical missing-user tokens could be active; it is compatible with the legacy schema. In all cases, baseline verification must precede stamping, and new empty environments must be migrated before serving traffic. A later explicit operator step installs/validates constraints. Do not append migrations to the Uvicorn command or use startup events to run them.

Verify expected code/revision, valid index, FK definition and validation status, zero orphans, unchanged controlled counts, usable sequences, and successful logs without secret output. Production GET `/` is only a greeting. Existing-account login/read-only list checks require authorization and must not change records. Signup, CRUD, deletion policy, and user-isolation checks run in disposable/staging databases; no synthetic records are added to production.
