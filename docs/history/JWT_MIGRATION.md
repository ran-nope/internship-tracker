# HS256 JWT dependency migration

Prepared locally on 24 October 2026. At the time of this report, no commit, push, deployment, credential
change, or production database access had been performed for this migration.

## Decision and advisory review

Replace `python-jose==3.5.0` with `PyJWT==2.15.1`. This application needs only
HS256 signing and verification, which PyJWT supports without optional cryptographic
dependencies. Its documented fixed-algorithm decoding and required-claim options
fit the existing authentication contract. [PyJWT usage](https://pyjwt.readthedocs.io/en/stable/usage.html),
[API reference](https://pyjwt.readthedocs.io/en/stable/api.html).

The previous dependency audit identified:

- `python-jose`: CVE-2026-85394 / GHSA-3qf3-8w2g-rqmx, a critical algorithm-confusion
  advisory involving DER public keys accepted as HMAC secrets. The advisory lists
  versions through 3.5.0 and no fixed release. [Advisory](https://github.com/advisories/GHSA-3qf3-8w2g-rqmx).
- `ecdsa`: CVE-2024-23342 / GHSA-wj6h-64fc-37mp, a timing side channel in ECDSA
  signing, key generation, and ECDH operations. Verification is unaffected; the
  maintainer does not plan a fix. [Maintainer advisory](https://github.com/tlsfuzzer/python-ecdsa/security/advisories/GHSA-wj6h-64fc-37mp).

The application already restricted verification to HS256 with a shared secret,
so these described attack paths did not appear applicable to its configuration.
Removing the unused library surface also removes the flagged dependencies rather
than relying on that assessment or suppressing audit findings.

## Minimal application change

`main.py` now imports `jwt` and catches PyJWT's `InvalidTokenError`. The required
expiration option changes from python-jose's `require_exp` to PyJWT's
`require: ["exp"]`; simply keeping the old option would not enforce expiration
presence in PyJWT. Signature and expiry verification remain enabled, and the
algorithm allowlist stays hardcoded to HS256. The existing strict positive-integer
`user_id` check, 401 response, Bearer challenge, and CORS behavior are preserved.

Tokens still contain only `user_id` and `exp`, are signed with the same environment
secret, and expire after 24 hours. Signup, password hashing, login response shape,
ownership checks, CRUD, frontend code, and database schema are unchanged.

`requirements.txt` pins PyJWT and removes python-jose and its unused dependency
tree: ecdsa, rsa, pyasn1, six, cryptography, cffi, and pycparser. Package metadata
and a fresh installation confirmed none is needed by the remaining runtime.
The local project virtual environment has the same removal and PyJWT installation.

## Compatibility and validation

Before removing python-jose, synthetic HS256 tokens were verified in both
directions between python-jose 3.5.0 and PyJWT 2.15.1. No real signing key or user
token was used. `tests/fixtures/legacy_hs256.json` retains a token generated by the
old library using the public test-only key. Its deliberately long test expiration
keeps the fixture stable; production token lifetime remains 24 hours.

Regression tests verify the old token authorizes the same isolated test user as a
new login token and does not expose that user's applications to another account.
The new token's algorithm, claims, return type, and 24-hour lifetime are checked.
Negative cases cover missing/invalid claims, malformed compact JWTs and signed
JSON, expired tokens, forged signatures, altered user IDs, invalid/future `iat`
and `nbf`, `alg: none`, unsigned tokens, HS384/HS512, and malformed headers.
Failures must return 401 with the Bearer challenge and expected CORS header.

| Check | Result |
| --- | --- |
| Complete backend API/security suite | 10 passed in isolated SQLite |
| Fresh requirements-only environment | Same 10 tests passed; all 19 runtime pins matched |
| Browser authentication/CRUD/isolation/error regressions | 4 passed using disposable PostgreSQL |
| Old/new library interoperability | Passed in both directions with synthetic tokens |
| Dependency consistency (`pip check`) | Passed in local and fresh environments |
| Updated backend requirements audit (`pip-audit`) | No known vulnerabilities; no ignored advisories |

The fresh browser backend used the new requirements and frontend port 5175/API
port 8001, leaving the developer's 5174/8000 services out of the test flow. The
full Phase 2 visual suite was not repeated because frontend code did not change.

## Compatibility and deployment requirements

- Existing unexpired tokens signed with the current key remain usable. Tokens
  from a previously rotated key remain invalid; this migration does not restore
  revoked sessions or require another rotation.
- PyJWT rejects expiry at the expiration second (`exp <= now`), whereas
  python-jose used `exp < now`. At most one second of boundary behavior changes.
  PyJWT also validates optional claims such as future `iat`; this application
  never issued those claims, so its existing tokens are unaffected.
- PyJWT requires Python 3.9 or newer. Verification used the project's Python 3.14
  environment. Short HMAC keys can trigger a PyJWT warning; no key was inspected
  or changed for that purpose, and no new key-length policy was added here.
- After approval, install the new requirements before restarting the backend.
  Prefer a clean build environment (on Render, clear the build cache if packages
  are reused). `pip install -r requirements.txt` alone does not uninstall packages
  removed from the requirements file. Verify the deployed environment no longer
  contains python-jose or ecdsa and run its dependency checks.
- Keep Render's `SECRET_KEY`, `DATABASE_URL`, CORS settings, and startup command
  unchanged. No database migration or frontend deployment is required for this
  backend-only change. There was no inspection or modification of hosted settings.
- Rollback would require reinstalling the previous dependency set before starting
  the old backend. The cross-library check supports wire compatibility in either
  direction, but rollback would reintroduce the known dependency advisories.

Production records and credentials were not changed. Audit results reflect the
advisory database at verification time, not a guarantee against future findings.
